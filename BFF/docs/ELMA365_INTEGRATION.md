# ТЗ: интеграция BFF ↔ ELMA365 (Заявки, Задачи)

Бриф для агента/разработчика, который будет разбираться с ELMA365 и предложит, что конкретно заводить
там, какие API-ручки нужны и какие процессы. Документ описывает то, что уже точно есть и работает на
стороне BFF, и явно перечисляет то, что нужно решить дополнительно — этот документ не диктует, как
устроена сама интеграция (направление синхронизации, механизм передачи), это должен предложить
исполнитель, зная реальные возможности ELMA365.

> Статус: интеграция отложена, не внедряется. Документ оставлен как референс на будущее.

## 1. Зачем

think-front/BFF ведёт заявки на обслуживание объектов (`WorkTask`) и назначения инженеров на них
(`TaskAssignment`). Нужно, чтобы эти же данные были видны/доступны в ELMA365 — двум сущностям там
соответствуют «Заявки» и «Задачи» (решение об этом соответствии уже принято, см. раздел 2).

## 2. Сущности и атрибуты на стороне BFF

### 2.1. Заявки → `WorkTask`

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `id` | UUID | да | Id заявки в BFF |
| `number` | string | да | Номер заявки, уникальный |
| `sourceType` | enum: `prediction`/`fact`/`call`/`external` | да | Источник создания |
| `objectId` | int | да | Внешний id объекта мониторинга (не BFF-шный UUID, из справочника системы мониторинга) |
| `picketId` | long? | нет | Пикет объекта, если применимо |
| `topic` | string | да | Тема/краткое описание |
| `description` | string? | нет | Подробное описание |
| `workType` | string? | нет | Вид работ |
| `faultClassification` | string? | нет | Классификация неисправности |
| `sensorIds` | int[] | нет | Датчики, к которым относится заявка |
| `comment` | string? | нет | Комментарий |
| `dispatcherId` | UUID? | нет | Диспетчер (ссылка на `User.Id`) |
| `status` | enum: `new`/`inWork`/`assigned`/`engineerWorking`/`completed`/`closed`/`returnedToWork`/`cancelled` | да | Статус заявки |
| `priority` | short | да | Приоритет |
| `createdAt` | datetime | да | Создана |
| `takenAt` | datetime? | нет | Взята в работу |
| `assignedAt` | datetime? | нет | Назначен инженер |
| `completedAt` | datetime? | нет | Отчёт сдан |
| `closedAt` | datetime? | нет | Закрыта |

Полный объект (`GET /tasks/{id}`) несёт также вложенные списки `predictions`/`assignments`/`reports`/
`returns` — если ELMA365 понадобятся отчёты по заявке (`TaskReportDto`) или возвраты (`TaskReturnDto`)
как отдельные сущности, их атрибуты не описаны здесь намеренно — не входили в исходный запрос, дать
знать, если понадобятся.

### 2.2. Задачи → `TaskAssignment`

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `id` | UUID | да | Id назначения |
| `taskId` | UUID | да | Ссылка на заявку (`WorkTask.Id`) |
| `engineerId` | UUID | да | Инженер, которому назначено (ссылка на `User.Id`) |
| `assignedBy` | UUID | да | Кто назначил — диспетчер (ссылка на `User.Id`) |
| `assignedAt` | datetime | да | Когда назначено |
| `status` | string | да | См. ниже — фактически константа |
| `comment` | string? | нет | Комментарий |

**Важно:** `status` у назначения — не enum, а свободная строка. В текущем коде единственное значение,
которое туда реально пишется — `"assigned"`, при создании; переходов в другие статусы в коде нет.
Если в ELMA365 нужен полноценный жизненный цикл задачи (взял/выполняет/выполнил/отклонил) — этого
сегодня в BFF просто не существует, придётся либо заводить в BFF новые статусы и переходы, либо вести
этот жизненный цикл целиком на стороне ELMA365, глядя на статус самой заявки (`WorkTask.status`) как на
косвенный индикатор.

`engineerId`/`assignedBy`/`taskId` — внутренние GUID, не человекочитаемые. Нужны будут имя инженера и
номер заявки — их придётся резолвить отдельно (`GET /users/{id}`, `GET /tasks/{id}`) либо брать из
`WorkTaskDto.Assignments`, где на каждое назначение уже готовы оба).

## 3. Что уже есть в BFF — API-ручки

Все под общей авторизацией BFF (JWT через cookie `access_token`, раздел 4).

| Метод | Путь | Право | Что делает |
|---|---|---|---|
| GET | `/tasks?dispatcherId=&status=&page=&pageSize=` | `tasks:read` | Список заявок, с фильтрами и пагинацией |
| GET | `/tasks/{id}` | `tasks:read` | Заявка целиком, включая вложенные назначения |
| POST | `/tasks` | `tasks:create` | Создать заявку |
| PUT | `/tasks/{id}` | `tasks:update` | Изменить заявку (не статус — см. отдельные ручки ниже) |
| POST | `/tasks/{id}/take` | `tasks:update` | Взять заявку в работу — `409 task_already_taken`, если кто-то успел раньше (это штатный исход гонки, не ошибка данных) |
| POST | `/tasks/{id}/assignments` | `tasks:update` | Создать назначение (= «задачу») инженеру: `{ engineerId, comment? }` |
| POST | `/tasks/{id}/reports` | `tasks:update` | Сдать отчёт по заявке — переводит её в `completed` |
| POST | `/tasks/{id}/returns` | `tasks:update` | Вернуть заявку — переводит в `returnedToWork` |

Отдельной ручки «изменить статус заявки напрямую» нет — статус меняется только через перечисленные выше
действия (`take`/`assignments`/`reports`/`returns`), каждое со своими побочными эффектами
(`takenAt`/`assignedAt`/`completedAt` и т.д. выставляются автоматически). Это важно для планирования
процесса в ELMA365: нельзя просто «поставить статус», нужно вызвать соответствующее действие.

Полное описание типов запросов/ответов — [`FRONTEND_INTEGRATION_DOMAIN_MODELS.md`](FRONTEND_INTEGRATION_DOMAIN_MODELS.md),
разделы «Заявки и работы».

## 4. Авторизация — как ELMA365 будет обращаться к BFF

Сегодня единственный способ получить доступ к API BFF — быть аутентифицированным пользователем `auth`
(claim `sub` в JWT), у которого есть профиль в BFF (`users`) и грант на нужный ресурс (`tasks`, право
`read`/`create`/`update` по таблице выше). Отдельного механизма M2M/service-to-service в BFF нет —
единственный прецедент (пока не реализованный) — «завести обычного пользователя-«робота»» и выдать ему
грант, как задумано для будущего consumer'а прогнозов (`docs/DECISIONS.md`, комментарий в
`PredictionsController.cs`).

Значит, для ELMA365 придётся:
1. Завести отдельный аккаунт в `auth` (сервисный/технический) — умеет ли `auth` выдавать долгоживущие
   токены для таких аккаунтов без интерактивного логина, нужно проверять в самом `auth`, не в BFF.
2. Завести профиль этого аккаунта в BFF (`users`, `auth_user_id` = `sub` этого аккаунта — тот же приём,
   что при бутстрапе первого администратора, `scripts/001_seed_initial_data.sql`).
3. Выдать этому пользователю грант на `tasks` с нужным набором прав.

## 5. Вопросы, которые должен решить исполнитель (агент по ELMA365)

Ниже — то, что определяет весь дальнейший дизайн интеграции, и что нельзя решить, зная только код BFF —
нужно смотреть в реальные возможности ELMA365 (её версия/тариф, есть ли исходящие вебхуки, входящий
REST API, коннектор к очередям и т.п.):

1. **Направление синхронизации.** BFF — источник истины, ELMA365 только отображает/строит отчётность
   (одностороннее)? Или в ELMA365 тоже можно создавать/менять заявки-задачи, и это должно попадать
   обратно в BFF (двустороннее)? Это определяет, нужны ли вообще новые ручки в BFF (для одностороннего
   «ELMA365 читает» существующих GET достаточно) или нет.
2. **Механизм передачи.** Если ELMA365 умеет принимать вебхуки — BFF может вызывать их при изменении
   заявки/назначения (тогда в BFF нужен новый код — обработчик события после `SaveChangesAsync` в
   `WorkTaskService`, аналог того, как уже сделана публикация email-уведомлений в RabbitMQ,
   `docs/DECISIONS.md`, раздел про `tf-mail`). Если ELMA365 может только сама периодически опрашивать
   внешний REST — существующих GET-ручек (раздел 3) может быть достаточно, максимум нужна ручка вида
   «изменённые с такого-то момента» (`updatedAt`-фильтр, которого сейчас нет ни у заявок, ни у
   назначений — если понадобится инкрементальная синхронизация, придётся добавить).
3. **Идентификация записей между системами.** Если ELMA365 создаёт у себя карточку на каждую заявку —
   нужно решить, где хранить связь `WorkTask.Id` ↔ id записи в ELMA365: новое поле в BFF (`WorkTask.
   ElmaTicketId`, `TaskAssignment.ElmaTaskId` — по аналогии с тем, как заводили `User.Email` под
   рассылки) или ELMA365 хранит `WorkTask.Id`/`TaskAssignment.Id` у себя как внешний ключ. Второй
   вариант проще для BFF (ничего не меняется), но нужно уточнить, поддерживает ли ELMA365 хранение
   произвольного внешнего id как ключа для последующего поиска/обновления записи.
4. **Маппинг полей в схему ELMA365.** Атрибуты из раздела 2 — что они есть в BFF; как их назвать/каких
   типов завести в самой ELMA365 (текст/справочник/дата и т.д.) и что делать со значениями enum
   (`status`, `sourceType`) — заводить справочником в ELMA365 или хранить как текст — решает исполнитель
   по возможностям платформы.
5. **Жизненный цикл «задачи».** Раздел 2.2 — на сегодня в BFF у `TaskAssignment.status` нет реальных
   переходов. Нужно решить: заводить их в BFF (тогда это отдельная задача на доработку BFF, не только
   ELMA365) или интерпретировать статус задачи в ELMA365 через статус родительской заявки.
6. **Учётная запись для доступа.** Раздел 4 — уточнить у `auth`, поддерживает ли он выдачу токена для
   технического аккаунта без интерактивного логина (client credentials/API-key/что угодно, что у него
   есть) — без этого ELMA365 не сможет вызывать BFF вообще.

## 6. Критерии приёмки (черновик — уточнить после ответов на раздел 5)

- [ ] Определено и задокументировано направление и механизм синхронизации.
- [ ] ELMA365 может аутентифицированно читать (и, если решено двусторонне, писать) заявки/задачи через
  API BFF из раздела 3, либо описан протокол push из BFF в ELMA365.
- [ ] Статусные переходы заявки (`take`/`assignments`/`reports`/`returns`) корректно отражаются в
  ELMA365 без прямой записи в `status` — только через соответствующие действия.
- [ ] Гонка `409 task_already_taken` на `POST /tasks/{id}/take` обработана отдельно от прочих ошибок —
  не баг, ожидаемый исход.
- [ ] Если выбрана инкрементальная синхронизация — определён способ узнавать «что изменилось» (сейчас
  такой ручки в BFF нет, см. п.2 раздела 5).
