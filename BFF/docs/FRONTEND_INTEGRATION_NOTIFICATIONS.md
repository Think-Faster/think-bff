# Email-рассылка (`POST /notifications/email`) — для think-front

Короткий документ под одну фичу — отправка письма произвольным получателям с антиспам-лимитом.
Общие соглашения (базовый путь через nginx, авторизация/куки, формат ошибок, гейтинг UI через
`/permissions/me`) — в [`FRONTEND_INTEGRATION_GROUPS_USERS_PERMISSIONS.md`](FRONTEND_INTEGRATION_GROUPS_USERS_PERMISSIONS.md),
разделы 1–4, здесь не повторяются.

Доставка асинхронная: BFF публикует уведомление в очередь, письмо реально шлёт отдельный сервис
инфраструктуры (не тот же процесс) — `200` от BFF значит «принято в обработку», не «письмо доставлено».

## Заодно: новое поле в профиле пользователя

`UserDto`, `UserListItemDto`, `CreateUserRequest`, `UpdateUserRequest` — добавлено необязательное
`email: string | null`. Если хочешь отправлять письма конкретным пользователям (через `userIds` ниже),
у них должно быть заполнено это поле — иначе такой получатель просто не получит письмо (см. статус
`noEmailOnFile`).

## `POST /notifications/email`

Право: `notifications:create` (гейтить кнопку так же, как обычно — через `/permissions/me`).

### Request

```ts
interface SendEmailRequest {
  subject: string;
  text: string; // только простой текст — HTML не поддерживается, уйдёт как есть, тегами
  userIds?: string[]; // guid[] — существующие пользователи BFF
  emails?: string[]; // произвольные email-адреса
  ticketId?: string; // необязательно, только для логов на стороне почтового сервиса
  kind?: string; // необязательно, например "fact"/"forecast", только для логов
}
```

Нужен хотя бы один получатель — либо в `userIds`, либо в `emails`, либо в обоих сразу (можно смешивать,
списки не обязаны быть непустыми оба сразу). Если оба пустые/не переданы — `400`.

`subject` обрезается сервером до 255 символов, `text` — до 20 000; переводы строк и повторные пробелы в
`subject` схлопываются в один пробел (в `text` — нет, `\n` там значащий). Обрезка происходит без ошибки,
молча — если важно не превышать лимиты, проверяй длину на своей стороне заранее и предупреждай
пользователя до отправки.

### Response `200`

```ts
type EmailSendStatus =
  | "sent"           // принято в обработку почтовым сервисом (не значит «доставлено»)
  | "rateLimited"     // тому же адресу уже отправляли письмо меньше минуты назад
  | "userNotFound"    // userId из userIds не существует
  | "noEmailOnFile"    // такой пользователь есть, но email в профиле не заполнен
  | "invalidEmail"     // строка из emails не похожа на email
  | "failed";          // очередь отвергла публикацию (сетевая ошибка/недоступность брокера)

interface EmailRecipientResultDto {
  email: string;
  userId?: string | null; // заполнено, если получатель пришёл через userIds
  status: EmailSendStatus;
}

interface SendEmailResponse {
  requested: number; // сколько уникальных получателей обработано — тот же адрес из userIds и emails
                      // одновременно (или повторённый в списке) считается один раз
  sent: number; // сколько успешно приняты в обработку (см. статус sent), не «доставлено»
  results: EmailRecipientResultDto[];
}
```

### Что важно показать в UI

- **`sent` не значит «письмо дошло».** Доставка асинхронная — BFF только публикует уведомление, дальше
  его забирает и реально отправляет отдельный сервис. `sent` = «принято в обработку». Если нужна
  гарантия доставки конкретному человеку — это вне возможностей этой ручки, узнавать нужно другим
  способом (у администратора инфраструктуры, по логам).
- **HTTP `200` не значит «всё отправлено».** Успех смотри по каждому элементу `results`, а не по коду
  ответа — запрос с частично неверными адресами или частично залимиченными получателями всё равно
  вернёт `200` с отчётом, где что получилось.
- **Каждому получателю отдельное письмо**, даже если в одном запросе их несколько — получатели не видят
  друг друга в письме (не «одно письмо всем в копии»).
- **Лимит — 1 письмо на email-адрес в минуту**, независимо от того, как получатель был указан (`userId`
  или прямой `email`). Повторный клик «отправить» тому же адресу раньше — этот получатель получит
  `rateLimited`, остальные из того же запроса это не затронет. Разумно показывать что-то вроде «письмо
  этому адресу уже отправлено недавно, попробуйте через минуту» именно для этого статуса.
- **`noEmailOnFile`** — стоит показать как «у пользователя не указана почта», а не как общую ошибку
  отправки (это подсказка «иди заполни профиль», а не сбой).
- **`400`** — не прошла валидация: пустой `subject`/`text`, невалидный формат в `emails`, либо оба
  списка получателей пусты.
- **`403`** — нет права `notifications:create`.
